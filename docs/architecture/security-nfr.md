# 安全与非功能要求

## 1. 授权模型

JWT 只作为身份凭证，`tenant_id/user_id` 用于定位主体；角色、权限、用户状态、部门和数据范围必须每次从服务端平台数据解析（后续可短期缓存）。请求头中的租户不得覆盖 JWT 租户。

数据范围按从小到大定义为 `SELF`、`DEPARTMENT`、`DEPARTMENT_AND_SUB`、`ALL`。列表查询与详情查询使用同一范围判定；字段权限在 DTO 映射前执行，手机号、邮箱等敏感字段默认脱敏。附件下载必须重新校验目标业务对象权限。

## 2. 强制防线

- Repository 的每条业务 SQL 必须显式包含 `tenant_id`。
- 私海读取同时校验功能权限和组织数据范围；公海变更使用条件更新防并发重复认领。
- 审批、合并、转换、交接等高风险命令记录前后快照、操作者和 `traceId`。
- 密钥只通过环境变量或密钥服务注入，不写入仓库；日志禁止打印令牌和完整敏感字段。
- 数据库是事实源；Redis 仅用于权限缓存、短锁、限流和热点字典。

## 3. 可用性与一致性

- 外部回调以租户、来源和外部业务键幂等；失败采用指数退避并进入可人工处理的死信/对账队列。
- Outbox 与业务变更同事务；发布器可重复投递，消费者必须幂等。
- 常用列表在百万级数据下 P95 不高于 300ms，业务命令 P95 不高于 500ms。
- 备份采用每日全量加持续归档，定期演练恢复；明确 RPO/RTO 后再进入生产发布评审。
- 核心领域行覆盖率不低于 80%，整体不低于 70%；CI 强制执行 ArchUnit、Flyway、隔离和并发测试。
